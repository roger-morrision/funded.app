## Build and deployment evidence

The source checkout, ignored `dist/` directory and running Docker image can represent three different revisions. A clean commit alone does not prove the browser was rebuilt after the last UI change. Generate the release manifest only after the final build; its browser-source digest must match the checkout. Do not use `--allow-dirty` output as a release artifact. Build deployment images from the exact committed archive, not a mutable shared worktree, and compare the live API build identity with that revision.

Browser settings currently attest the network, public test-wallet gate and source digest. They do not attest every origin-related environment variable; check the actual API and metadata origins separately when moving from localhost to public hosting. Rebuild after changing the metadata origin. Verify deep routes, static assets and unmocked browser startup against the running image, rather than reusing a previous image's report.

The earlier verified `8289dc1` image had a 526.61 kB minified application chunk (154.63 kB gzip in build output); this is a build-size observation, not measured participant transfer or loading time. Investigate actual first-task delays before selecting additional code-splitting work.

The pilot pass found avoidable analysis work in the browser input path. One synthetic Node 24.19.0 diagnostic with 100 device records at the 2,000-event cap took about 10.2 seconds; analyzing one full record averaged 92 ms over ten runs. These are offline fixture timings under the current workspace load, not browser or production capacity measurements. The live panel now displays only its local event count; detailed cohort aggregation runs in the bounded offline CLI. Measure real first-task latency before making further performance claims.

## Remaining event-history and amount gaps

A reproduced late insertion behind the X collector's timestamp cursor was never verified on subsequent polls. The collector now gives older eligible source IDs a separate cyclic reconciliation position and finite sweep ceiling. This position is persisted atomically with prepared events, without moving the fresh-event timestamp backward. Durable outbox lookup suppresses existing IDs in every delivery state; fixed activation and finalized proof/consent requirements still apply. Candidate work shares the collection budget with fresh records and verification retries. A missing durable lookup or a full 200-item retry ledger must remain explicit, and a 500-ID timestamp boundary still requires operator reconciliation rather than silently advancing. Preserve cursor/outbox data; do not delete history or change activation to silence a diagnostic.

This is discovery over the already loaded application snapshot, not an indexed history service. Full snapshot reads and in-memory sorting remain scaling limits. Events absent from the snapshot, sources removed before a sweep reaches them, old daily windows and pre-activation receipts are outside this guarantee. Persisted rotation gives each of the three event streams and two daily summary providers priority across committed polls, including one-item batches; within a stream, retries, fresh rows and older candidates take turns. Keep restart, insertion-on-either-side-of-the-sweep, budget, pending-capacity and uncertain-delivery regressions.

Shared payout receipt verification and cached history now use the same exact decimal conversion. Regression fixtures cover valid 15-lamport payouts, rejection of fractional or coerced base units, recipient/sender balance bindings, and persisted proof reuse after restart. Receipt display and CSV accept canonical bounded base-unit values, reject unsafe JSON numbers, and mark omitted records as incomplete with a retry action. This closes the reproduced receipt-path precision gap; it is not an audit of every amount calculation in the app.

## Recovery and proof boundaries

Direct payout balance-delta proofs establish delivery, not original fee funding. Those reward rows remain visible with `feeSourceVerified: false` until the necessary collection and entitlement joins are independently established. Verified reward-cycle funding retains its separate proof path.

Analytics base-unit aggregates expose exact decimal strings in `exactLamports`. The three legacy numeric totals remain numbers only while safely representable; overflow yields `null`, `precisionStatus: overflow` and the affected `precisionUnavailableFields`. Consumers must use the exact representation or show unavailable, never coerce null to zero. This precision status covers the base-unit totals, not every derived SOL allocation field.

A disk-full app recreation was observed during the prior release. Run the read-only [capacity preflight](workspace-deployment.md#check-capacity-before-upgrading-an-existing-deployment) before building and before switching the existing app. It is a point-in-time threshold check, not a reservation or a guarantee of future writes; preserve images, volumes and backups when capacity is insufficient.

Keep keyboard regression coverage for pilot setup after recording is enabled and receipt recovery after its initiating control is hidden. Receipt dates now accept explicit ISO timestamps with valid calendar and timezone components. Missing or malformed dates show “Recorded payment time unavailable” and export a blank `paid_at` field without discarding an otherwise verified payment. Valid timestamps retain their original ISO representation in CSV. These are ledger-recorded payment times, including recovery observations, not verified transaction block times. A synthetic receipt on the preceding built image reproduced `paidAt: null` as January 1970; keep the browser regression for that coercion, valid timezone localization and exact amounts.

The daily X adapters now reject malformed windows before RPC reads or cached evidence reuse. They require explicit UTC timestamps, valid calendar dates, minute alignment and an exact 24-hour interval, matching the formatter. Reusing a poll token for another window rechecks its evidence. Keep regressions for invalid input after a cache hit, start-inclusive/end-exclusive payout boundaries, valid source collections before the payout interval, and failure/recovery without daily cursor advancement or duplicate dispatch. The collector still chooses the latest completed UTC day; the adapters do not infer dates or promise a complete blockchain index. Coverage refers to the full recorded payout ledger within its bounded verification budget. The previous direct-adapter failure returned complete coverage for invalid dates, but the collector/formatter already prevented that malformed input from becoming a public summary.

## Transactional pilot persistence

The earlier browser failure reproduced two simultaneous opt-ins creating different participant IDs despite sequential Web Locks. A later lock holder could read stale empty localStorage, overwrite the first tab's record, and stop the first recorder when the replacement propagated. Native diagnostics reproduced that failure twice in ten runs; a green CI run did not close it.

The pilot now stores its record and consent grant together in one authoritative IndexedDB transaction. UI success and export wait for commit; stale queued opt-ins must match the stored consent version, and queued events belong to the participant who consented when the event occurred. Migration preserves eligible legacy identity and allowed fields once; revoked or mismatched records become an empty off state. The persistent off state prevents stale legacy data from being imported again. Legacy cleanup happens after commit and reports retained copies honestly.

Keep the real-browser concurrency, migration, abort, unavailable-storage, export, deletion and missing-notification regressions enabled. The repaired native enrollment case passed ten repetitions with one committed identity and an explanation for the conflicting profile. These fixtures establish browser behavior, not a count of real participants or a retention gain. Preserve consent versions and migration markers during later refactoring; sleeps, relaxed assertions and a passing retry are not substitutes for transactional consistency.

Cross-tab messages are only invalidations. If both notification mechanisms are unavailable, another tab may display stale controls until its next transaction; the stored consent still governs writes and exports. Older localStorage-only builds cannot read migrated records. Follow the [pilot rollback guidance](creator-pilot.md#metrics-and-denominators), keep recording paused while downgraded, and restore an IndexedDB-capable build rather than recreating identities.

## Devnet faucet confirmation and request isolation

An offline reproduction of the active `requestAirdrop()` handler displayed “Airdrop confirmed” and refreshed the balance for a confirmation containing `value.err` or missing confirmation evidence. A timeout after receiving a signature discarded its Explorer link. Overlapping wallet connections could also issue duplicate faucet requests even when the stale connection result was correctly ignored.

Keep success conditional on an explicit `value.err === null`. A known execution error is a failed transaction; malformed evidence or a transport failure after a signature is an unknown outcome with its receipt link retained. Do not advise another faucet request as a substitute for checking a known transaction. A request that times out before returning a signature does not establish whether the faucet accepted it. Missing or malformed signatures produce wallet Explorer guidance without creating transaction links or attempting confirmation. Confirmation at the requested `confirmed` commitment is not a finalized receipt or proof of a specific balance increase.

Hold one request guard before wallet connection starts and release it on every exit. Suppress results after wallet-session changes, reject non-Devnet calls before wallet/RPC activity, and keep a balance-refresh failure separate from an already confirmed transaction. Regression tests execute the actual handler with synthetic wallet/RPC responses; they do not establish native wallet acceptance or a live faucet transfer. Existing server capability gates remain required and disabled in the normal preview; no alternative RPC, server signer or automatic transaction retry is introduced. Receipt links are current-page feedback, not durable recovery across reloads.

## Deterministic rate-limit acceptance

RPC budgets use fixed minute windows. An HTTP verifier that sends its budget assertions across a real minute boundary can correctly receive a reset budget and incorrectly fail the release. Keep the verifier's clock control confined to its disposable server child, check the full ordinary/write/preview budgets within each window, then explicitly advance across the boundary and verify the reset. Do not add a production clock override, weaken limits or rely on sleeping/retrying until a run is green.

## Explore pagination input contract

Malformed pagination previously became `NaN` or fractional values, producing an empty HTTP 200 Devnet feed or invalid upstream provider parameters. Both Explore endpoints now accept a single unsigned decimal safe integer for each supplied `limit` and `offset`. Missing values default to 40 and 0; valid values retain the existing 1–100 and 0–10,000 clamps, including a zero limit becoming 1. Leading zeroes are accepted. Explicit empty values, duplicates, signs, whitespace, fractions, exponent/hex syntax and unsafe integers return HTTP 400 before storage, connection or provider work. Keep actual-route regressions for this ordering and for valid page selection; validation does not establish indexed feed scalability.

## Listing-burn uncertainty and recovery

The active listing handler previously reported “No burn submitted” when RPC broadcast timed out after possible acceptance. It also ignored recovery-storage failures and broadcast without retaining a receipt. Persist and verify the original signed transaction identity before broadcast; if storage cannot be read or confirmed, pause payment. Never replace that identity with a different RPC return value. Preserve the receipt and block another burn across uncertain broadcast, confirmation and indexing results. Only a matching verified Devnet listing or a finalized failure can clear the saved record; failed cleanup must retain the lock and explain the remaining record. A non-finalized error is still an uncertain outcome for this purpose.

Keep offline handler and native component-browser tests for denied/corrupt storage, failed writes and cleanup, reload recovery, mismatched RPC identities, early errors, stale wallet sessions and repeated receipt verification. The journal is sessionStorage in the current tab, with an in-memory fallback during that page session; it is not cross-tab or permanent recovery after closing the tab. Never infer global duplicate-payment prevention or live wallet acceptance from these fixtures. Keep the tab and original signature while verification is unresolved; do not clear site data as a recovery shortcut.

Receipt Retry asks the listing verifier about the saved transaction. After reload, a signed-only, never-landed or failed transaction may remain conservatively locked if that verifier cannot establish a successful listing. A separately reviewed finalized-failure/expiry recovery path is still needed; this repair does not infer failure from an absent receipt or promise complete automatic recovery.
